What Waraq is

Waraq is a key-value store on a B+tree of 4 KiB pages. It keeps the pages you use in memory and reads the rest from NVMe one page at a time. It commits every transaction with snapshot isolation, and runs a worker on every core with nothing shared that a read has to write.

    04 · What you get

    Three things
    you can count on.

    What the design buys you, in plain terms. Each one comes from a layer you just scrolled through.

    Fig 0.1

    Memory speed, disk size

    Pages you touch stay in memory. Pages nobody touches cool, then leave. Your data can be many times larger than RAM.

    “Keep it all in RAM, or it gets slow.”the old trade

    “Hot pages at memory speed, the rest one read away.”cooling stage · one read per miss

    Fig 0.2

    Every core, no queue

    A reader checks a version number instead of taking a lock, so it writes nothing another core has to see.

    “Add a thread, add a wait.”shared latches

    “Readers check a version and move on.”optimistic lock coupling

    Fig 0.3

    Commits that survive a crash

    When commit returns, the transaction is in the log on disk. After a crash, Waraq reopens at the last committed state.

    “It was still in memory when the power went.”lost on crash

    “Committed means on disk, and it reopens intact.”write-ahead log · recovery on open

      Embedded in Rust
      One crate, four files, no server. The engine does no I/O of its own: backends behind one trait do, over a file, a raw device or memory.
      
    
      On Linux
      io_uring over O_DIRECT, one ring per core. A page miss submits one read and yields, so the core keeps working.
      
    
      In the browser
      A WebAssembly build over the Origin Private File System. Tabs share one store through a single leader.
